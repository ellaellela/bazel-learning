# Bazel Fundamentals - Level 9.9: Aspect Composition (Problem Statement)

## The Scenario
Your DevInfra organization is scaling. The **Code Analysis Team** has written a highly optimized Aspect that extracts metadata (like line counts and complexity) from source files. 

The **Security Team** wants to write a linter that evaluates that metadata, but they do *not* want to write a custom parsing engine. They want to compose their linter directly on top of the Code Analysis Team's Aspect. Furthermore, developers want to run this pipeline directly from the CLI without needing a Stitcher Rule in their `BUILD` files.

## DevInfra Concepts
1. **Aspect Composition (`requires`)**: The Linter Aspect will force Bazel to run the Parser Aspect first.
2. **Direct CLI Invocation (`OutputGroupInfo`)**: The Linter Aspect will return an Output Group, allowing developers to trigger the pipeline and retrieve the files using purely command-line flags.

---

## The Task

Create a file named `composition.bzl` at the root of your workspace.

### 1. The Code (`composition.bzl`)
Copy this scaffolding. Notice that we are writing **zero rules**—only Aspects!

```python
# ---------------------------------------------------------
# TEAM A: The Base Parser
# ---------------------------------------------------------
MetricsInfo = provider(fields = ["metadata_file"])

def _parser_aspect_impl(target, ctx):
    # Simulate an expensive AST/Metrics parsing operation
    out_file = ctx.actions.declare_file(target.label.name + ".metrics")
    
    ctx.actions.run_shell(
        outputs = [out_file],
        command = "echo 'COMPLEXITY_SCORE=42' > " + out_file.path
    )
    
    return [MetricsInfo(metadata_file = out_file)]

parser_aspect = aspect(
    implementation = _parser_aspect_impl,
)

# ---------------------------------------------------------
# TEAM B: The Consuming Linter
# ---------------------------------------------------------
def _linter_aspect_impl(target, ctx):
    # TODO: Read the MetricsInfo provider from the target.
    # Bazel guarantees this exists because of the 'requires' attribute!
    # metrics_file = target[...].metadata_file
    
    report_file = ctx.actions.declare_file(target.label.name + ".lint_report")
    
    # Simulate linting the metrics file
    ctx.actions.run_shell(
        inputs = [metrics_file], # Depend on the file from Team A!
        outputs = [report_file],
        command = "echo 'LINT_PASSED: Analyzed -> ' $(cat {}) > {}".format(
            metrics_file.path, 
            report_file.path
        )
    )
    
    # TODO: Expose the report file directly to the CLI!
    # Return a list containing an OutputGroupInfo with a dictionary.
    # Map the key "lint_reports" to a depset containing `report_file`.
    return []

linter_aspect = aspect(
    implementation = _linter_aspect_impl,
    # TODO: Tell Bazel this Aspect MUST run after parser_aspect
    requires = [] 
)
```

### 2. The Invocation
Because we used `OutputGroupInfo` and we aren't aggregating files up a `deps` tree (for simplicity in this exercise, we are just linting the top-level target), we don't need to touch the `BUILD` file at all! 

We can run this directly on our `ml_trainer` target from Level 9.7. 

Run this exact command in your terminal:

```bash
bazel build //:ml_trainer \
  --aspects=//:composition.bzl%linter_aspect \
  --output_groups=lint_reports
```

**Success Criteria:**
1. Bazel will intercept the request for `linter_aspect`.
2. It will see the `requires` dependency and dynamically execute `parser_aspect` first.
3. It will pipe the metrics file into the linter.
4. Because of `--output_groups`, it will drop the final report right into your terminal output paths. 
5. Run `cat bazel-bin/ml_trainer.lint_report`. It should successfully read the mock complexity score generated by the parser!
