# Bazel Fundamentals - Level 9.9: Aspect Composition (Explanations)

## 1. The Solution

Here is the completed Starlark code for composing Aspects and exposing them to the command line:

```python
# ---------------------------------------------------------
# TEAM A: The Base Parser
# ---------------------------------------------------------
MetricsInfo = provider(fields = ["metadata_file"])

def _parser_aspect_impl(target, ctx):
    out_file = ctx.actions.declare_file(target.label.name + ".metrics")
    
    ctx.actions.run_shell(
        outputs = [out_file],
        command = "echo 'COMPLEXITY_SCORE=42' > " + out_file.path
    )
    
    return [MetricsInfo(metadata_file = out_file)]

parser_aspect = aspect(
    implementation = _parser_aspect_impl,
)

# ---------------------------------------------------------
# TEAM B: The Consuming Linter
# ---------------------------------------------------------
def _linter_aspect_impl(target, ctx):
    # 1. Read the exact file produced by Team A's Aspect
    metrics_file = target[MetricsInfo].metadata_file
    
    report_file = ctx.actions.declare_file(target.label.name + ".lint_report")
    
    ctx.actions.run_shell(
        inputs = [metrics_file], 
        outputs = [report_file],
        command = "echo 'LINT_PASSED: Analyzed -> ' $(cat {}) > {}".format(
            metrics_file.path, 
            report_file.path
        )
    )
    
    # 2. Expose the report directly to the CLI
    return [
        OutputGroupInfo(lint_reports = depset([report_file]))
    ]

linter_aspect = aspect(
    implementation = _linter_aspect_impl,
    # 3. Force Bazel to execute the parser before the linter wakes up
    requires = [parser_aspect] 
)
```

---

## 2. DevInfra Theory: Aspect Composition (`requires`)

In massive monorepos, DevInfra tools must be modular. If you pack parsing, linting, and security scanning into one giant Aspect, it becomes a bottleneck that takes hours to run and is impossible to maintain.

By using the `requires` attribute, Bazel allows you to build **DevInfra Microservices**. 
When `linter_aspect` requires `parser_aspect`, Bazel's execution engine guarantees strict ordering on every single node in the graph:
1. `_parser_aspect_impl` runs.
2. Bazel attaches the `MetricsInfo` provider to the current Target.
3. `_linter_aspect_impl` wakes up.
4. It safely queries `target[MetricsInfo]` because the native engine guarantees it is already there.

This allows different infrastructure teams to own their own specific tools while safely chaining off each other's work without duplicating expensive graph traversals.

## 3. DevInfra Theory: Direct CLI Invocation (`OutputGroupInfo`)

Up until now, you had to write "Stitcher Rules" in your `BUILD` files to trigger Aspects and collect their files. 

While Stitcher Rules are great for CI pipelines or mandatory targets, they are terrible for developer experience. If a developer just wants to run a quick linter check on their local machine, they shouldn't have to modify a `BUILD` file to do it.

By returning `OutputGroupInfo(my_channel = depset(...))` directly from your Aspect, you create a dedicated data channel to the command line.

```bash
bazel build //:my_target --aspects=... --output_groups=my_channel
```

When Bazel sees the `--output_groups` flag, it bypasses the need for a Rule entirely. It runs the Aspect, reaches into the returned providers, grabs the named group, and drops the generated files directly into the developer's terminal.

---

## 4. Deep Dive: Aspects vs. DefaultInfo

While Custom Rules almost always return `DefaultInfo` to declare their primary outputs, **Aspects cannot return `DefaultInfo`.**

Every target in the graph (e.g., a `cc_library` or `py_binary`) already possesses a `DefaultInfo` provider generated by its underlying rule. Because an Aspect merges its returned providers onto the existing target, attempting to return `DefaultInfo` from an Aspect causes a fatal collision (`Provider 'DefaultInfo' already provided`).

This is the primary reason `OutputGroupInfo` is essential for DevInfra tooling. It allows Aspects to safely attach new, parallel file channels (like `.scan` or `.lint_report` files) to a target without interfering with the target's native compilation outputs.
